Несколько лет назад я писал тексты на WordPress. Потом перенес [свой блог](https://zavarov.com/) на [Hugo](https://gohugo.io/) — генератор статических сайтов, в котором статья остается обычным Markdown-файлом, а готовая страница собирается заранее.

Со временем из настроек, шаблонов и собственных требований к чтению выросла отдельная тема — [**Hugo Mini**](https://github.com/zavarovkv/hugo-mini). Недавно я вынес ее в открытый репозиторий и [каталог тем Hugo](https://themes.gohugo.io/themes/hugo-mini/).

Хочу показать не только результат, но и устройство темы: почему здесь нет обязательного фронтенд-фреймворка, как работают шрифты и мультиязычность и что нужно, чтобы запустить такой блог самостоятельно.

## 1. Блог — это прежде всего текст

Когда делаешь личный сайт, очень легко увлечься интерфейсом. Еще одна анимация, виджет, библиотека, новый инструмент сборки. А потом оказывается, что для публикации заметки нужно обслуживать целый небольшой продукт.

Мне хотелось другого: написать Markdown, сохранить файл, отправить изменения в Git — и получить страницу. Без панели администратора, базы данных и клиентского приложения, которое сначала загружается, а потом показывает текст.

В Hugo это довольно естественная модель:

```text
content/blog/article.md
         ↓
   Hugo + шаблоны
         ↓
   public/article/index.html
```

На сервере остается статический HTML. Большую часть страницы можно прочитать даже с отключенным JavaScript. А сам блог легко хранить в GitHub и переносить между хостингами.

Но «статический» не означает «бедный»: у Mini есть темная тема, RSS, SEO-метаданные, Open Graph, поддержка формул, диаграмм и комментариев — просто каждая возможность занимает свое место.

## 2. Почему важна типографика, а не количество компонентов

Основа Mini — собственные шаблоны Hugo и [Beauty.css](https://github.com/zavarovkv/beauty-css), небольшая независимая библиотека для типографики. Интерфейс строится вокруг ширины строки, интервалов, заголовков и ссылок. Шрифт Inter лежит в самом проекте, а не загружается с внешнего CDN.

Ширина чтения ограничена примерно 720 px на больших экранах. На смартфоне страница сохраняет боковые отступы в 20 px, а текст остается выровненным по левому краю. Это сознательное ограничение: слишком длинная строка утомляет, а выравнивание по ширине способно создавать некрасивые пробелы.

Есть и менее заметная деталь — **типографика на этапе сборки**. Hugo обрабатывает текст по правилам языка: например, в русской статье не разрывает число и единицу измерения между строками. Исходный Markdown при этом не переписывается, а код, ссылки и формулы сохраняются как есть.

Это хороший пример моего подхода к личным инструментам: небольшие детали должны работать автоматически и не требовать внимания автора при каждой публикации.

## 3. Что происходит с CSS и JavaScript

Частый соблазн — подключить еще один пакет ради одной удобной функции. Я старался разделить обязательное и необязательное.

- **CSS и шрифты** лежат локально. Hugo объединяет и минифицирует стили, а хеш в имени файла помогает браузеру обновлять кеш после релиза.
- **Темная тема** учитывает настройки системы. Явный выбор пользователя можно запомнить.
- **KaTeX и Mermaid** подключаются только на страницах, где действительно нужны формулы или диаграммы.
- **Telegram-комментарии и аналитика** выключены, пока автор не настроит интеграцию.

Иными словами, обычная статья не должна платить производительностью за функции, которых на ней нет.

Отдельная история — Open Graph. Тема умеет формировать карточки для ссылок при сборке сайта. Не нужно вручную рисовать изображение для каждого короткого поста.

## 4. Один блог — два языка

На моем сайте русский и английский контент живут отдельно. Hugo генерирует страницы для каждого языка, а Mini добавляет переключение языка и `hreflang` для поисковых систем.

Языки — часть структуры сайта, а не машинный перевод, который незаметно выполняется в браузере. Это важно: у каждой версии есть собственный URL и HTML, поэтому ссылки можно отправлять, индексировать и архивировать.

Перевод статей для моего блога автоматизирован отдельным процессом в GitHub Actions. **Самой теме ключ API не нужен**: она только корректно отображает уже подготовленные версии.

## 5. Запускаем свой блог

Для начала можно просто посмотреть [живое демо](https://hugo-mini-demo.vercel.app/). В нем нейтральный пример сайта — без моих личных контактов и содержимого блога.

А если хочется сразу попробовать свой проект, я подготовил [Starter с кнопкой Deploy to Vercel](https://github.com/zavarovkv/hugo-mini/tree/main/starter). Кнопка копирует минимальный пример в новый репозиторий и разворачивает его. Затем достаточно поменять название, страницу About и первую статью.

Локальный вариант тоже простой. Нужен Hugo Extended версии 0.146 или новее:

```bash
hugo new site myblog
cd myblog
git init
git submodule add https://github.com/zavarovkv/hugo-mini.git themes/hugo-mini
```

Дальше указываем `theme = "hugo-mini"` в `hugo.toml`, добавляем Markdown в `content/blog/` и запускаем `hugo server`. Полный минимальный конфиг есть в [README проекта](https://github.com/zavarovkv/hugo-mini#quick-start).

В Starter версия темы зафиксирована конкретным релизом и проверяется по SHA коммита. Hugo для Vercel тоже загружается из официального релиза с проверкой SHA-256. Так сборка не зависит от случайного обновления инструментов.

## 6. Чего здесь сознательно нет

Mini не пытается быть универсальным конструктором. Если нужен интернет-магазин, редактор страниц с drag-and-drop или портал с десятками интерактивных блоков, вероятно, стоит выбрать другой инструмент.

И еще важный компромисс: хотя основа сайта статическая и автономная, комментарии Telegram, аналитика и некоторые дополнительные функции при их включении обращаются к внешним сервисам. Полной автономности со всеми интеграциями здесь не обещаю.

Зато для авторского блога, технических заметок или личного сайта такой набор мне кажется разумным: **меньше инфраструктуры между мыслью и опубликованным текстом**.
